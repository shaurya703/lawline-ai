## CHAPTER 5 — IMPLEMENTATION (Salient Modules)

The system is a Python 3.12 package `lawline` (≈2,300 lines) with twelve modules; each is independently unit-tested.

| # | Module | File | Function |
|---|---|---|---|
| 1 | JSON/parquet loaders & corpus builder | `lawline/data/ingest.py`, `constitution.py` | Converts six public sources into one schema (`Document`): 42,776 documents — 36,180 statute sections/articles and 6,596 judgments. Includes a page-header/footnote-aware parser for the official Constitution text (496 articles) and a cause-title parser for High-Court orders. |
| 2 | Chunk manager | `lawline/data/chunking.py` | Paragraph-aware windows of ≤220 words with 40-word overlap; every chunk carries Act/section/court/year metadata and a header restating the provision identity. 69,149 chunks. |
| 3 | Embedding module | `lawline/index/embedder.py` | Sentence-Transformers wrapper (MPS/CUDA/CPU), BGE query instruction, L2-normalised vectors. |
| 4 | FAISS index | `lawline/index/faiss_index.py` | Exact inner-product index (69,149 × 384); supports ID-selector filtering by document type. |
| 5 | BM25 index | `lawline/index/bm25_index.py` | BM25Okapi with a legal tokenizer that preserves identifiers such as *498A*; supports masked (filtered) scoring. |
| 6 | Knowledge graph | `lawline/index/knowledge_graph.py`, `concepts.py` | networkx graph: 1,024 Acts, 36,180 sections, 6,596 cases, 2,133 topics, 214 curated legal concepts; 25,147 section cross-references, 16,735 case→section citations, 448 concept→provision edges. Entity extraction (Act aliases, s./Art. numbers, case names, concepts) + one-hop expansion. |
| 7 | Hybrid retriever | `lawline/retrieval/hybrid.py`, `fusion.py` | Reciprocal Rank Fusion (k=60) of the three rankings; document-type filter; query-type routing (narrative → dense only). |
| 8 | Reranker | `lawline/retrieval/reranker.py` | Cross-encoder (`ms-marco-MiniLM-L-6-v2`) over the top-30 fused candidates. |
| 9 | Query engine | `lawline/engine.py`, `generation/` | Prompt with numbered passages, citation-constrained generation (Gemini 3.5 Flash-Lite; Groq/extractive fallbacks), citation parsing and verification. |
| 10 | Evaluation module | `lawline/eval/` | Gold-set builder, metrics, ablation runner, fusion sweep, chunk sweep, answer-quality judge, tables and plots. |
| 11 | API wrapper | `lawline/api.py` | FastAPI: `/health`, `/query`, `/retrieve` with per-retriever toggles and document-type scope. |
| 12 | User interface | `lawline/app.py` | Streamlit chat with source panel, citation ticks, per-stage latency and search scope. |
| + | Training | `lawline/training/train_biencoder.py`, `train_reranker.py` | Legal fine-tuning of the bi-encoder (MNRL, dense-mined hard negatives) and of a cross-encoder (BCE). |

## CHAPTER 6 — RESULTS

### 6.1 Data and benchmark
**Corpus.** 34,183 sections of 1,019 central Acts (India Code dump), 1,059 BNS/BNSS/BSA sections, 444 IPC sections, 496 Constitution articles, 589 Supreme Court Reports 2016 judgments (with entity annotations), 6,000 High-Court fact excerpts and 7 landmark judgments → 42,776 documents / 69,149 chunks (Table `corpus_stats`).

**Benchmark** (Table `gold_stats`): 1,810 frozen queries in four tasks, all scored at the document level.

| Task | Query → target | Test queries | Leakage control |
|---|---|---|---|
| BNS-QA | natural-language question → BNS/BNSS/BSA section | 600 | split by *section*: no test section in training |
| IPC-Facts | High-Court fact pattern (section numbers masked, header stripped) → IPC section(s) | 500 cases | split by *case*; test cases excluded from corpus and training |
| Const-QA | question → Constitution article(s) mined from expert answers | 124 | random split |
| SC-Case | one-paragraph summary → judgment | 586 | never used for training |

Metrics: Recall@k, MRR@10, nDCG@10, macro-averaged over tasks.

### 6.2 Retrieval ablation (RQ1) — Table `ablation_base`, `per_task_base`, Fig. `ablation_base.png`, `per_task_base.png`
Off-the-shelf encoder (`bge-small-en-v1.5`):

| Configuration | R@1 | R@5 | nDCG@10 |
|---|---|---|---|
| BM25 | 0.448 | 0.559 | 0.525 |
| FAISS (dense) | 0.431 | 0.541 | 0.503 |
| Knowledge graph | 0.153 | 0.192 | 0.187 |
| FAISS + BM25 | 0.473 | 0.584 | 0.547 |
| FAISS + BM25 + KG | 0.471 | 0.610 | 0.560 |
| FAISS + BM25 + KG + reranker | **0.515** | **0.625** | **0.586** |

* Fusion of dense and lexical retrieval beats either alone; adding the graph retriever gives a further +2.6 points R@5, concentrated on statute questions (BNS-QA 0.43 → 0.56; Const-QA 0.80 → 0.89).
* The graph alone is weak (it fires only on entity mentions) but precise (Const-QA 0.51 from article mentions alone).
* Reranking adds +1.5 points macro and +6 points on BNS-QA.
* **IPC-Facts fails completely with general-domain models** (R@5 ≤ 0.02 for every configuration, even when retrieval is restricted to statutes): fact narratives share almost no vocabulary with the governing provision.

### 6.3 Fusion sensitivity — Table `fusion_sweep_base` / `fusion_sweep_ft`
Equal RRF weights are best. Boosting exact KG hits (×2, ×3) *reduces* R@1 from 0.47 to 0.37/0.31 because one concept maps to several sibling provisions. RRF k ∈ {20, 60, 100} changes nDCG by < 0.01. The shipped configuration is unweighted RRF, k = 60.

### 6.4 Legal fine-tuning of the bi-encoder (RQ2) — Table `base_vs_finetuned`, Fig. `base_vs_finetuned.png`, `training_loss.png`
Training: 13,016 (query, provision, hard-negative) triplets from the training splits; MultipleNegativesRankingLoss; hard negatives = the base model's own top wrong hit; embeddings + lower 6 layers frozen (10.8 M trainable parameters); batch 16, seq 128, 1 epoch, lr 5e-5; 33 min on a laptop CPU.

| Task | Dense R@5 base | Dense R@5 fine-tuned |
|---|---|---|
| BNS-QA | 0.410 | **0.680** |
| IPC-Facts | 0.000 | **0.325** (R@10 0.413) |
| Const-QA | 0.790 | **0.899** |
| SC-Case | 0.964 | 0.930 |
| Macro | 0.541 | **0.709** |

Gains are on held-out sections/cases. The only regression is the task with no training data (SC-Case, −3.4 points), which fusion with BM25 recovers (0.978).

### 6.5 Reranking strategies and query routing — Table `reranker_variants`, Fig. `reranker_variants.png`

| Strategy (fine-tuned embeddings) | BNS-QA | IPC-Facts | Const-QA | SC-Case | Macro R@5 |
|---|---|---|---|---|---|
| No reranker (FAISS+BM25+KG) | 0.697 | 0.204 | 0.921 | 0.980 | 0.700 |
| Generic cross-encoder | 0.695 | 0.023 | 0.901 | 0.980 | 0.650 |
| Legal-fine-tuned cross-encoder (1 epoch) | 0.428 | 0.258 | 0.840 | 0.278 | 0.451 |
| Dense only (fine-tuned) | 0.680 | 0.325 | 0.899 | 0.930 | 0.709 |
| **LawLine (routed)** | 0.695 | 0.325 | 0.901 | 0.980 | **0.725** |

The generic reranker — trained on web passages — rewards lexical overlap with procedural boilerplate and collapses IPC-Facts; a one-epoch legal reranker fixes that task but forgets general relevance. Because query types separate cleanly by length (questions ≤ 40 words; fact narratives ≥ 115 words), the final system **routes**: narrative queries (> 100 words) → fine-tuned dense retriever; everything else → full hybrid + reranker. Final: **macro R@5 0.725, MRR@10 0.681, nDCG@10 0.685** (Table `ablation_ft`) — +16.6 R@5 points over BM25 and +10 over the base-encoder hybrid. For short questions (≤ 40 words) the top exact KG match is also guaranteed a slot in the final list if fusion/reranking dropped it; offline replay shows this is benchmark-neutral (macro R@5 0.725 → 0.724) while fixing vocabulary-gap queries such as *anticipatory bail under BNSS* (→ s.482, whose text never contains "anticipatory").

### 6.8 Latency — Table `latency_ft`, Fig. `latency_stages.png`, `latency_e2e.png`
Apple M-series laptop, 8 GB, no discrete GPU: query embedding 13 ms (p50), FAISS 2 ms, KG 68 ms, cross-encoder 10 ms/pair (≈0.3 s for 30 candidates); BM25 0.2–0.3 s for questions and up to 2.8 s (p95) for 300-word narratives (a further reason the narrative route bypasses it). End-to-end in the answer-quality run: retrieval + reranking 3.0 s, generation 2.5 s. Offline indexing of the whole corpus: 14 min.

## CHAPTER 7 — TESTING, VALIDATION AND DEPLOYMENT

### 7.1 System testing
`pytest` suite: 19 tests across chunking, fusion, metrics, BM25/FAISS (incl. filtered search), knowledge graph (construction, mention extraction, expansion, concept layer), engine (extractive and LLM paths, citation parsing) and the FastAPI endpoints (happy path, validation errors, retriever toggles). All tests run offline in seconds on a five-document fixture.

### 7.2 Verification
Unique document ids; every gold label verified to exist in the corpus; IPC coverage of all 159 test sections confirmed after the incomplete bare-acts IPC was replaced; Constitution parser spot-checked (Arts. 14, 21, 21A, 243B, 368); leakage controls enforced mechanically (test split materialised before the corpus is built). Bugs found and fixed by testing: FAISS/torch OpenMP crash on macOS, citation parser missing `[1, 3]`, malformed High-Court titles, a KG weight heuristic that reduced R@1 (caught by the fusion sweep), post-hoc type filtering that returned no statutes (replaced by in-search filtering).

### 7.3 Validation
Retrieval validated on 1,810 gold queries (§6.2–6.6); generation validated on AIBE and judged QA (§6.7); behaviour on ambiguous or unanswerable questions validated qualitatively (the system abstains: *"The provided passages do not contain…"*).

### 7.4 Deployment
* **API**: `uvicorn lawline.api:app` — `GET /health`, `POST /query`, `POST /retrieve` (OpenAPI docs at `/docs`).
* **UI**: `streamlit run lawline/app.py` — chat, sources with ✅ on cited passages, per-stage latency, search scope (all / statutes / case law), retriever toggles.
* **Container**: `Dockerfile` + `docker-compose.yml` (CPU torch; prebuilt indices and fine-tuned model copied in; serves :8000 and :8501).
* **Configuration**: `.env` (Gemini/Groq keys), `LAWLINE_FAISS_TAG=ft`, `LAWLINE_EMBED_MODEL=outputs/models/lawline-bge-small-legal`.

## CHAPTER 8 — CONCLUSION AND FUTURE WORK

**Conclusion.** LawLine AI was rebuilt end to end from public data: a 42,776-document Indian-law corpus, a knowledge graph with a curated concept layer, hybrid retrieval with RRF and reranking, a legally fine-tuned retriever, query-type routing and citation-constrained generation. On a new 1,810-query, four-task benchmark the final system reaches macro Recall@5 0.725 / nDCG@10 0.685 versus 0.559 / 0.525 for BM25, and grounding raises AIBE accuracy from 64.7 % to 68.0 % while making every claim traceable to a cited provision (judged faithfulness 2.0/2). The ablation also surfaced two cautionary results worth reporting: a general-domain reranker can undo a domain-adapted retriever, and heuristic fusion boosts can hurt precision — both were caught only because the evaluation is quantitative.

**Future work.** (1) Broader case-law coverage (all SCR years, more High Courts) and real-time ingestion of amendments. (2) Joint training of the reranker with replay of general data, and a learned query-type router. (3) Human evaluation with practitioners and law students, including groundedness annotation in the style of Trautmann et al. (4) Multilingual queries (Hindi/Kannada) via translation at the query layer. (5) Conversation memory and clarification questions for ambiguous queries. (6) Hosting on Hugging Face Spaces / a cloud VM so the reviewers can use it live.
